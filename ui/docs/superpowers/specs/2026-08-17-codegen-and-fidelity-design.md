# 代码生成与还原精度设计

2026-08-17

把已解析的元素树变成可交付的代码,并把还原精度上的几个细节定死:字体、图标、图片、间距。

本文是**设计**,不是实施计划。第 8 节给出子项目划分,每个子项目单独出计划。

---

## 1. 架构:元素树就是 IR

`ElementTree` 已经具备中间表示的全部要素——树形结构、盒模型、flex 布局量、重复、滚动、样式。**不再定义第二层 DSL**,那是重复劳动。

```
                    ┌─→ HTML + CSS      给人看、验收保真度（本轮）
元素树 (IR) ────────┼─→ WXML + WXSS     用户要小程序时
                    └─→ RN / uni-app    用户要 APP 时
```

代码生成是**可插拔的 emitter**,元素树是唯一真相源。

### 1.1 转端必须回到 IR,不能拿 HTML 去转

HTML 是 IR 的一次**投影,投影有损**。逐条列出转换会丢什么:

| IR 里有 | 生成 HTML 后 | 从 HTML 转端时的后果 |
|---|---|---|
| `repeat: {count, pitch}` | 展开成平铺元素,信息消失 | 想用 `wx:for` 收成循环,还原不回来 |
| `scrollX` / `scrollY` | `overflow: auto` | `scroll-view` 该用 `scroll-x` 还是 `scroll-y`,要猜 |
| `kind: text/icon/image/component` | 全是 `div` | `view` / `text` / `image` 选哪个,要猜 |
| `classification: tool/model/human` | 不体现 | 哪些人工确认过、哪些还存疑,全丢 |
| 原始像素测量值 | `12.3077vw` 字符串 | 反解要除回去,引入舍入误差 |

### 1.2 带牙齿的推论:emitter 不许发明信息

如果某个 emitter 写到一半发现缺东西——要猜一个字体栈、要判断某个容器其实是按钮——**那个信息必须补进 schema,不能在 emitter 里就地猜**。就地猜出来的东西别的 emitter 看不见,两份产物会立刻开始漂移。

这条规则的实际作用:每次 emitter 想"临时处理一下",都是 schema 该扩展的信号。文字内容、图标资源之所以被列为独立子项目而不是塞进 emitter,就是因为它们是 IR 的缺口,不是渲染的细节。

### 1.3 中间态用原生 HTML + CSS,不带框架

1. **框架解决的问题这里不存在。** 框架的价值在状态管理和组件复用;截图还原产出的是静态结构,没有状态可管,也没有要对齐的组件库(已确认)。
2. **消费者是"还没决定去哪"的用户。** 任何框架都是提前站队,收益要等转端才兑现,成本当场就付。
3. **框架会让保真度更难验证。** 原生 HTML 能直接和原图叠起来比像素;多一层运行时就分不清偏差是测量错了还是框架默认样式。

框架登场的位置是**某个 emitter 的目标**,不是中间态的形态。

### 1.4 跨端安全子集

"原生"不等于随便写 HTML。只用三端语义重合的那部分,HTML→WXML 才是机械替换而非翻译:

```
div → view      span → text      img → image
overflow:auto 的容器 → scroll-view
flex / absolute / border-radius / background-color   三端语义一致
```

**禁用**:grid、伪元素、复杂选择器、`position: fixed` 的特殊用法——用了就又变成有损转换。

### 1.5 单位:比例是唯一真相

```
ratio(px) = px / designWidth          designWidth = 图片宽度（本例 1170）

Web      →  (ratio × 100).toFixed(4) + "vw"
小程序    →  (ratio × 750).toFixed(2) + "rpx"
RN/APP   →  ratio × Dimensions.get("window").width
```

三者是**同一个线性映射的三种写法**,换算常数精确,没有舍入漂移。写死 `px` 才是误差来源——到小程序必须按屏宽重算,那一步才丢精度。

换算函数抽成 `toUnit(px, target)`,后续 emitter 复用。

**纵向也用 `vw`,不能用 `vh`。** 页面是可滚动长页,`vh` 随设备高度变;用 `vw` 表达纵向尺寸才保住设计稿宽高比。

## 2. 布局映射

每个节点一个 `<div class="e-{id}">`,**所有节点写死宽高**。

写死宽高与 flex 不冲突——flex 子项有 `width` 就用 `width`,布局语义仍是 flex,转端无损。反过来靠 `padding + gap` 撑出尺寸会把测量误差逐层累加。

```
容器 (component / grid)
  display: flex
  flex-direction:  layout.direction
  gap / padding:   layout 实测值
  background:      style.background
  width / height:  box 实测值

叶子 (text / icon / image / decoration)
  width / height:  box 实测值
  color / font-size / font-weight:  style 实测值

positioning: "absolute"
  position: absolute + 相对父节点的 left / top
```

三条刻意的取舍:

1. **圆角只在 `image` / `component` 上输出,且只用人工设定的值。** 实测同款图标格子 `n2 = 37`、`n3 = 64`——圆角是在"图标+文字"的组合框上量的,量到的其实是里面图标的圆,自动测量在容器上不可信。
   现有代码已经按这个方向走得更远:`supportsBorderRadius()` 把圆角限定为 `image` / `component`,`clearTreeBorderRadii()` 在**载入时清空所有已存圆角**(提交 `55add6b`)。
   **副作用需留意**:`detect` 产出的自动圆角会被服务端存下并在本次会话可见,但下次载入即被清空——等于自动圆角实际上不生效。emitter 因此只会看到人工设过的值,这与本条结论一致,但两者的实现路径不同,改动任一处时要一起看。
2. **`repeat` 展开成平铺**,但在 CSS 里留注释标出"这是 N 项重复",供后续的人或 AI 决定要不要收成循环。
3. **区域按 `regions.json` 的 y 排序垂直堆叠**,每区域一个 `<section>`,高度取 `region.h`,背景取 `tree.background`。

## 3. 字体

### 3.1 先验框,再谈字号

32 个 `text` 节点的墨高分布:

```
 28 px ███████(7)   ← 与 34 同档，被内缩 bug 削去 6px（已修）
 29 px █(1)
 34 px ██████████(10)
 40 px ███(3)
 51 px █(1)
 87 px █████(5)  ⚠
 90 px █████(5)  ⚠
```

87/90 那 10 个查行投影(51px 的「登录/注册」查过,单段、比值 0.94,**通过**):

- **优惠券码 h=87 → 墨迹 2 段**:`476..478`(3px 残留)+ `528..561`(真正的文字,34 高)。**框上方多包了 50px 空白。**
- **猜你喜欢 h=90 → 单段连续 90px**,4 字宽 216 → 每字 54 宽 vs 90 高,比值 0.6。汉字是方的,单行该接近 1。**高度里混进了非文字内容。**

**32 个里有 10 个不是单行文字**,拿它们拟合字号会得到 96px 这类离谱值。

两条纯几何判据,不通过就标存疑、**不写 fontSize**(而不是写一个错值):

1. **行投影必须单段** —— 抓多包空白的框。
2. **每字宽 / 墨高 ∈ 约 [0.8, 1.3]** —— 字符数用列投影周期数出来(复用 `mergeByGap`)。抓混入非文字的框。

> 阈值 `[0.8, 1.3]` 目前只有两个观测点支撑(联系客服 1.04、登录/注册 0.94 通过;猜你喜欢 0.6 拒绝)。实施时需在全量 text 节点上重新标定并把证据写进注释。

### 3.2 字号量化到全页阶梯

> 设计稿的字号是离散的少数几档,测量值是连续的。还原必须把连续量吸附回离散阶梯。

现在逐节点独立拟合,同一排本该同字号的标签得到 `36.6 / 36.2 / 37.0 / 37.4 / 36.6` 五个小数。写进 CSS 就是五个不同 `font-size`——代码一眼假,转端后误差各自累积。

```
1. 通过验框的节点各自拟合出连续字号
2. 1D 聚类（阈值取数据自身的断层，见 6.3）
3. 每簇取中位数作为该档阶梯值
4. 全部吸附到最近阶梯，写回 style.fontSize
```

**白送的质量指标:簇内离散度。** 某节点明显偏离簇中位数 = 它的框量错了。之前那个 6px bug 本可以被自动报出,不必手工数像素。

**字重同样量化**——一页通常只有 regular + medium 两档。`FontMatch.margin` 小的节点跟随同簇多数票。

### 3.3 墨迹框 ≠ 行盒

我们量的是**墨迹框**(笔画上下沿)。CSS 里 `<span>` 占的是**行盒**(高度 = `line-height`),字形基线位置由 half-leading 决定,两者不重合。

**绝不能把墨迹框的 y 直接当作文字元素的 `top`**,那样文字整体偏下。

精确反算需要该字体的 ascent/descent,而字体族由用户选、还可能是本机没装的苹方——**生成时算不出来**。所以不去算:

```css
.text-node {
  width: …; height: …;      /* 就是量到的墨迹框 */
  display: flex;
  align-items: center;      /* 让墨迹在盒子里居中 */
  justify-content: …;
  line-height: 1;           /* 去掉 half-leading 干扰 */
}
```

**让墨迹居中于测得的框,而不是靠偏移量对齐。** 跨端一致,误差只来自 ascent/descent 不对称——对汉字极小,对有下伸部的西文会偏。

**自洽性**:盒子既然定义为墨迹框,`gap` / `padding` 量的也是"墨迹到墨迹"的距离,比设计稿"盒子到盒子"大。整套自洽,渲染位置正确;只是数值和设计稿原始值对不上,影响"代码像不像人写的",不影响还原。

### 3.4 字体族:不做像素判别

实测否定了用离散度选字体的想法:修正框之后离散度从 0.079 降到 0.008,但字体之间只差 0.0003(雅黑 0.0077 / 回退 0.0080 / 宋体 0.0081),完全在噪声内。

原因是结构性的:**汉字几乎撑满 em 框**,各家字体墨高比例都在 0.92–0.99 窄带内,这个量不携带字体信息;区分字体的信息在笔画形状。而且本机探测显示 PingFang SC、Noto Sans SC、Source Han Sans SC **全部未装**——截图是 iOS 的,真实字体是苹方,候选集里没有正确答案。

**方案:字体族由用户选,不自动判别。**

### 3.5 字体库:用 web font,不装系统

渲染发生在浏览器,**服务器一个字体都不用装**。也不该装在操作系统上——换机器就没了、不同用户结果不一致。正确做法是字体文件跟着项目走(`@font-face`),不需要"安装"这个动作。

真正的约束是另外两件事:

**体积。** 中文字体一个字重 10MB 起步。缓解:按需加载(用户点了才下载)+ 子集化(整套一万多字,页面只用几百个,裁剪后几十 KB)。子集化要等文字内容子项目完成。

**版权——这条是要害。**

- **苹方(PingFang SC)苹果专有,不可分发。** 而目标页面用的正是它。
- 微软雅黑同理。
- 可合法打包:**思源黑体**(Source Han Sans / Noto Sans SC)、**阿里巴巴普惠体**、**HarmonyOS Sans**,均免费可商用。

**方案**:内置 3–5 个免费可商用中文黑体作候选池,验收时用户切换比对;苹方一档用思源黑体近似。用眼睛比对本就是判断题,交给人是对的。

**预览字体 ≠ 产出代码里的字体。** 预览可能用思源黑体,但生成的代码应写 `-apple-system, "PingFang SC", "Noto Sans CJK SC", sans-serif`——代码最终跑在真手机上,iPhone 本来就有苹方。小程序端若要非系统字体,需 `wx.loadFontFace`,留到小程序 emitter。

### 3.6 字体相关还缺的属性

| 属性 | 怎么拿 | 何时做 |
|---|---|---|
| `text-align` | 比较墨迹框在父容器里的左右余量 | 现在就能做 |
| `line-height` | 多行文字行投影的两段间距 | 现在就能做 |
| 多行截断 | 需要文字内容 | 等文字内容子项目 |
| `letter-spacing` | 列投影周期减字宽;移动端少见 | 最低优先级 |

## 4. 图标

### 4.1 现状:彩色插画为主

20 个图标按主色数排:

```
用户头像 168×147  1 色  ⚠      客服耳机 76×63  4 色
左箭头    18×63   1 色  ⚠      定位     62×68  4 色
扫一扫    64×58   3 色         …
首页      58×59   3 色         退款     68×68  8 色
购物车    95×77   3 色
```

**18/20 是彩色图标(3–8 色)。** 这个事实排除了矢量化(描轮廓会碎成几百片,颜色还原不了)。

### 4.2 方案:模型给关键词 → 本地检索 → 人工挑

已确认的取向:**结构准、代码干净、内容随时可换** 优先于像素级像。图标是可替换的占位,人工纠正代价小。

```
模型看图 → 输出英文关键词（如 "qrcode scan"）
        → 代码在本地图标索引里检索，返回 top N
        → 人在界面上从候选里挑
        → IR 里存名字 + 关键词
```

符合项目一贯分工:**模型判断"这是什么",代码做检索**。关键词是模型擅长的,离线可跑,结果可复现。

**两条不可行的路,记下来避免重复尝试:**

- **让模型直接输出图标名**(如 `mdi:qrcode-scan`):模型会编造不存在的名字,高频幻觉。可作为加速——给了名字先查本地索引,查得到直接用,查不到退回关键词检索。
- **图像相似度匹配**:二十万图标逐个渲染比对不现实;更根本的是彩色插画与单色线条图本就不像,相似度分数没有意义。

### 4.3 图标库

**Iconify** 作统一入口:聚合 200+ 图标集、20 万+ 图标,有离线数据包,检索在本地完成。国内 App 风格上 Remix 和 Tabler 较接近。

**避开阿里 iconfont**:素材多但大量为用户上传,**版权状态不明**,商用有风险。

> 具体依赖包名、数据体积、检索 API 形态需在实施阶段核实,本文不锁定。

### 4.4 界面

属性面板里图标节点增加一行:

```
[原图切片]  →  [当前选中的图标]  [换一个]
```

"换一个"弹出候选网格,**原图切片必须一直钉在旁边**——否则人无法判断像不像。附搜索框供手动输关键词。这就是人工二次纠正的入口。

### 4.5 IR 里存什么

只存名字和关键词,**不存 SVG 内容**:

```ts
style.icon?: {
  source: "iconify";
  name: string;          // 如 "mdi:qrcode-scan"
  keywords: string[];    // 模型给的，便于重搜
  by: "model" | "human";
}
```

SVG 在生成代码时按名字现取。IR 保持轻量,换图标风格不用动已有解析结果。

### 4.6 两处会失真,提前知道

- **彩色变单色**:原图标 3–8 色插画,库图标单色。用量到的 `style.color` 让主色方向对,但**插画感会丢**。界面并排显示,不会偷偷发生。
- **方与不方**:库图标是正方形,原框不一定(购物车 95×77)。**按短边取尺寸、居中摆放、不拉伸**——宁可小一圈也不变形。

### 4.7 切图退成兜底

切图能力仍要做,原因有二:图片必须切;图标库找不到时要有退路。

### 4.8 白送的分类修正

上面两个"1 色"的:用户头像 168×147、左箭头 18×63,**整框只有一种颜色**——它们不是图标,是纯色块,分类错了。

由此得到一条免费判据:

> **"图标"框内只有一种颜色 → 它是纯色块,降级为 `decoration`,用 CSS 背景色表达,不切图。**

又小又准还能改色,并且这两个错误自动修好。

最终三档:**纯色块 → CSS;图标 → 图标库;图片 → 切图。**

### 4.9 模型给的图标名字不参与还原

不需要知道图标是什么就能还原它。名字的用处只有两个:界面上给人认;写进 `alt`。**不要为"认出图标是什么"额外投入**,那与还原度无关——但在 4.2 的方案里,名字/关键词是检索的输入,这是它唯一进入生产路径的地方。

## 5. 图片

- **切矩形,圆角交给 CSS。** 商品图实测四角 21/21/0/0。连圆角一起切,图片四角是白的,放到非白背景上会露出白角。
- **去重**:像素级比对,同图只存一份。
- **不内联**:商品图几十 KB,单独出文件。小图标可内联为 data URI 使页面单文件可跑,但注意小程序主包 2MB 限制、base64 膨胀约 1/3。

## 6. 间距

### 6.1 内缩 bug 对间距的实际污染

| | 修复前 | 修复后 |
|---|---|---|
| `padding = 0` | 51 | **86** |
| `padding = 6` | **19（假值）** | 0 |
| `padding = 9` | 1（假值） | 0 |
| 不同取值种数 | 21 | 15 |

**20 个内边距是凭空多出来的**,而 6 正好是那个内缩常数。**间距的准确性上限就是框的准确性**——所以验框永远排在归拢前面。

### 6.2 现状:间距碎成太多种

修复后:`gap` 28 个值 / 20 种,`padding` 112 个值 / 15 种。

设计师不会用 20 种间距。碎是因为测量有 1–2 px 抖动:

```
14, 15, 15, 16                    ← 同一个值
19, 19, 19, 22                    ← 同一个
26, 28, 29, 29, 31, 32, 32, 32    ← 同一个
88, 98, 98, 101                   ← 同一个
```

归拢后预计 `gap` 20 种 → 约 6 种,`padding` 15 种 → 约 4 种。

### 6.3 三层归拢,不能一锅烩

1. **重复组内部强制相等。** 宫格 5 格是同一模板重复出来的,间距必然完全相等;不等就是测量误差,取中位数抹平。**几乎零风险,且 `repeat` 已能识别,现成的。**
2. **同容器左右内边距通常对称。** 左 44 右 45 即同一值,差得少就取平均。
3. **全页归拢。** 最容易归错,放最后。

**阈值不要硬套 4 或 8 的倍数。** 那是替设计师做假设,他未必遵守——本页 15 / 30 这一组就不是 8 的倍数。正确做法是**从数据自身找断层**:排序后看相邻差值,簇内差 1–2、簇间差 10–20,阈值取在断层上。这正是 `element-runs.ts` 里 `mergeByGap` 的思想,**直接复用,不发明新东西**。

### 6.4 要点破:容器 = 内容外接框 ≠ 设计稿卡片框

修复后 86/112 的内边距是 0,不是 bug:我们检测出的容器边界紧贴内容,所以内边距自然为 0。真正的卡片内边距体现在更外一层——数据里 38/40/42/44/45 这一簇(17 个值)多半就是它。

不影响还原(整套自洽,渲染位置正确),影响的是**生成代码像不像人写的**。若要让结构更接近真实项目,还需一步"把容器还原成设计稿卡片框"——不是现在该做的。

## 7. 验收:叠加比对

生成页面与原图**叠放 + 透明度滑块**,拖动即可看出哪里错位。这是量化"还原度到底几成"最便宜的办法,而这正是项目立项时要回答的问题。

放在详情节点里,用 `iframe` 渲染生成结果,与"元素解析图"同坐标系叠加。

> 详情节点原本是上下两张图(区域原图 / 元素解析图),提交 `33a3e62` 移除了上面那张,现在只剩元素解析图——它底下铺的就是同一张区域裁图。所以叠加层要**加在元素解析图这个舞台上**,不要再引入第三张图。取色的落点也已经改到这里(提交 `f4f3dad`)。

> 更进一步的自动像素 diff(headless 截图 + 差异百分比)不在本轮范围——它需要引入无头浏览器,且叠加滑块已能定位问题。

## 7.5 与「AI 元素重构」工作流的关系

本文起草时,仓库里已经并行落地了一整套 AI 元素重构功能(`element-refactor-*` 共 14 个文件,前端 `ElementRefactorPanel.vue` + `element-refactor-state.ts`)。它做的是**模型审核结构合理性**,与本文的还原精度工作是两条线,但共用同一棵树,必须对齐三点:

1. **写入路径不变。** `putElements` 不带版本号,`treeVersion` 只用于重构流程自身的冲突检测。验框、间距归拢、字号量化照常走 `element-state.ts` 的 `commit()`。
2. **尊重编辑锁。** 重构会话进行中 `editingLocked` 为真,`commit()` 直接返回。任何新的自动写入(例如检测后自动量化)都必须走同一条路径,不能绕过。
3. **预览态不是真实树。** 详情节点在 `refactorStore.rootId` 非空时展示的是候选预览树。新增的界面元素(存疑标记、图标行)要跟随同一个开关,否则会在预览态上显示真实树的数据。

## 8. 子项目划分与顺序

这几块是**独立可实施的子项目**,各自出计划、各自验收。不要合并成一个大计划——上一次 3898 行的计划产出了"完全混乱"的界面,教训还在。

| 顺序 | 子项目 | 依赖 | 验收标准 |
|---|---|---|---|
| 1 | **文字框校验**(3.1) | 无 | 10 个问题框被标出;「登录/注册」等正常框不被误标 |
| 2 | **间距归拢**(6.3 第 1、2 层) | 无 | 重复组内间距完全相等;`padding` 种数下降 |
| 3 | **字号/字重量化**(3.2) | 1 | 全页字号收敛到个位数档位;离散度异常能报出 |
| 4 | **布局 emitter**(1、2 节) | 2、3 | 生成 HTML 能在浏览器打开,结构与原图一致 |
| 5 | **叠加比对界面**(7) | 4 | 能拖动滑块定位错位 |
| 6 | **图标检索与替换**(4) | 无 | 关键词检索出候选;人工可换;IR 存名字 |
| 7 | **切图导出**(4.7、5) | 无 | 图片正确切出;纯色块降级为 CSS |
| 8 | **文字内容** | 无 | 单列,方案未定 |

**1 和 2 排在最前**,因为它们修的是数据本身的错误;后面所有工作都建立在这份数据上。先做 emitter 只会把错误数据渲染得更显眼。
