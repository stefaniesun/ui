## 候选切分线检测的实测与修正

这是本次走查最有价值的发现。

**初版实现在真实截图上漏掉了全页最显眼的模块边界。** 原判据要求留白带的颜色"等于页面背景色（所有行均值的中位数）"。但这张页面顶部约 490px 是黄色渐变，加上套餐卡片和权益表的金色，中位色被拽成了偏黄的奶油色 `rgb(251, 247, 231)`——白色正文（255,255,255）和灰色分隔带（246,246,246）与它的 ΔE 都在 8 以上，**双双不被认作"背景"**，留白带规则整个失效。而白→灰的色差只有 ΔE≈3.5，也够不上突变阈值 12。结果套餐卡片与「权益对比」之间那条肉眼一望即知的灰色分隔带完全检不出来。

改为**带内颜色自洽**判据（连续低方差行且整段颜色一致，容差 ΔE 1.5，最小带高 3 行），不再依赖全局背景色。防止照片内部误判的作用由"连续多行既低方差、颜色又完全一致"来承担。

效果对比（原图坐标，图高 2532）：

| | 修正前 | 修正后 |
|---|---|---|
| 候选线总数 | 7 | 19 |
| 白卡片顶（tabs 起始）y≈489 | ✅ | ✅ |
| **灰分隔带（套餐/权益对比之间）y≈1185** | **❌ 漏检** | **✅ y=1194，强度 0.79** |
| 权益表下方 y≈2178 | ✅ | ✅ |
| 支付按钮下方 y≈2340 | ✅ | ✅ |

19 条候选对应约 8–10 个真实模块边界，正是设计预期的比例（工具给候选，模型挑选）。

## 执行过程中修掉的其他缺陷

| 缺陷 | 影响 | 处置 |
|------|------|------|
| `node --experimental-strip-types` 不把 `.js` 导入说明符映射到同名 `.ts` | `pnpm dev` 根本起不来，服务不可用 | 换成 `tsx` |
| 前端引用 `@region-split/core` 的 barrel 导出 | `node:fs`/`sharp`/`fastify` 被拉进浏览器包，`vite build` 直接失败 | 新增 `@region-split/core/browser` 只导出纯逻辑与类型 |
| `canUndo`/`canRedo` 是对普通数组求值的 `computed` | 无响应式依赖，首次求值后永远缓存，撤销/重做按钮**永不亮起** | 改用 `undoDepth`/`redoDepth` 两个 ref |
| `/image` 的 `rect` 参数无校验 | 非法或越界的 rect 让 sharp 抛错，返回 500 | 校验后返回 400 |
| `ModelConfigStore.read()` 对损坏配置文件不兜底 | 手工改坏配置文件会让所有路由 500，且无法从界面改回来 | 回落到环境变量/空串，真正的 I/O 异常仍向上抛 |
| 候选线只在 analyze 时计算 | 没配模型时手动拆分吸附是死的 | 移到上传时计算（纯图像分析，不需要模型） |
| 计划遗漏：`Esc` 退出拆分模式 / 清空选中 | spec 要求但没有任务覆盖 | 补实现，并补上 `App.vue` 键盘处理器的首个测试 |
| 计划遗漏：列表与画布 hover 联动、选中项滚动进视野 | spec §5.1 要求但没有任务覆盖 | 并入 Task 9 实现 |

计划本身还有 3 处内部矛盾（`ReconcileOptions` 字段名与其测试对不上、`uniqueId` 在 `a-2` 冲突时产出 `a-3` 而非规格要求、`analyze.ts` 调用点沿用了错误字段名），均以测试为准修正。

## 最终整体审查发现并修复的问题

13 个任务做完后做了一次全分支审查，又发现 14 项，全部修完。最严重的两条：

| 缺陷 | 影响 | 处置 |
|------|------|------|
| **拆分/合并后的自动 AI 重命名整套未实现**，但 README 已宣称实现 | 拆开的下半块永远叫"未命名区域"，合并结果沿用旧 id 且名字与内容不符；验收标准无法达成 | 实现完整流程：两个新块并发标记"命名中…"、请求串行发出（服务端是读-改-写，并发会互相覆盖）、失败静默回退占位名、自动路径不重复压撤销栈、id 变化时选中态跟随 |
| **模型调用没有任何超时** | 端点连得上但不回包时（本地模型正在加载、中转站挂起）请求永不返回，`busy` 永远为 true，只能刷新页面 | 加 15s 可配置超时，超时消息可读，且不触发重试 |

其余修复：

- `/api/model-config/test` 会把已保存的明文 Key 发给请求体指定的**任意** URL——改为只在 `baseUrl` 与已保存值相同时才回落到已保存的 Key
- 400ms 去抖窗口内点「AI 重命名」或「重新分析」，服务端从磁盘读到的是微调前的文档，微调被静默吞掉——两个入口先 `await persistNow()`
- `busy` 是死代码，分析期间界面无任何反馈且可继续编辑（返回后被覆盖）——接进界面并禁用会改动区域的操作
- `persistNow` 失败回滚会覆盖用户后续编辑，且能抛出未捕获的 rejection
- `rectSchema` 用 `z.number()` 允许小数坐标，能通过全部不变量校验并落盘，随后让 `sharp.extract` 抛错、该区域的 rename-ai 永久 502
- `analyzeProject` 在未传 `detectLines` 时把候选线抹成空，且每次都重跑整图分析
- `[▲][▼]` 长按连续触发未实现，挪 50px 要点 50 次（直接影响"≤10 次操作"的验收标准）
- 拆分模式下从列表多选会让界面卡死（操作条显示"拆分「undefined」"，切分线恒红）
- `[拆分]` 按钮在高度 <16px 的区域上没有禁用
- `rename()` 名字没改也压撤销栈并发起 PUT
- 非图片上传返回 500 而非 400，且失败前已建好空目录
- 502 响应体可能带绝对文件系统路径

修复后：**16 个文件 / 170 个用例通过**，typecheck 与 build 通过，实机复验了非图片上传 400、小数坐标 422、test 路由不外泄 Key（明文出现次数 0）。

## 尚未验证的部分

**接真实多模态模型的分段与命名质量没有验证过**——本次走查没有可用的模型端点。以下几项要等接上模型后才能确认：

1. 模型分段结果落在 5–10 个模块的比例；
2. 吸附后边界是否贴合，人工修正到满意所需的操作次数（目标 ≤ 10 次）；
3. 拆分/合并后自动命名的耗时与名称贴切程度；
4. `displayName` / `type` 判断的准确率。

界面层的交互（拖动、hover、拆分线跟随鼠标）只有组件测试覆盖，**没有在真实浏览器里手工点过**。建议接上模型后按 README 的操作表逐项过一遍。
